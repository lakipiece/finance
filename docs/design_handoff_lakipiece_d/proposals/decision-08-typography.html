D-08 — 폰트 · 타이포 스케일

짧게 답하면 지금 상태로는 플랫폼마다 다르게 보입니다. 확정 스펙의 색·간격·라운딩은 어디서나 동일하지만, 폰트만은 그렇지 않습니다. 현재 스택 'Noto Sans KR', -apple-system, BlinkMacSystemFont, sans-serif에서 Noto Sans KR은 어느 OS에도 기본 설치돼 있지 않기 때문입니다 — 웹폰트로 불러오지 않으면 항상 뒤의 시스템 폰트로 떨어집니다.

1. 지금 무슨 일이 일어나는가

아래 두 카드는 굵기 단계만 도식화한 것입니다 — 각 OS 폰트가 font-weight 네 단계를 몇 단계로 소화하는지를 그렸습니다. 자폭·x-height·줄바꿈 차이는 그 OS에서만 볼 수 있어 이 지면에서는 재현할 수 없습니다.

tabular-nums가 특히 중요합니다. 확정 스펙은 모든 금액을 고정폭 숫자로 우측 정렬하는데, Windows 기본 폰트에서 이게 동작하지 않으면 표의 자릿수가 행마다 어긋납니다 — 밀도를 올린 D안에서 가장 눈에 띄는 결함이 됩니다.

2. 세 가지 안

① 시스템 폰트 그대로웹폰트 없음
  • 로딩 비용 0 · 깜빡임 없음
  • 각 OS에서 가장 익숙한 글꼴
  • 플랫폼마다 다르게 보인다 — 질문하신 요구를 만족 못 함
  • Windows에서 500·600 위계 소실
  • tabular-nums 미동작 — 금액 정렬 깨짐
② Noto Sans KR 웹폰트현행 폰트 유지 권장
  • 모든 플랫폼 동일 — 굵기·자폭·숫자 정렬 전부
  • 이미 이 디자인의 기준 폰트라 시안 재검토 불필요
  • tabular-nums 지원 — 금액 정렬 보장
  • 웹폰트 로딩 (한글 서브셋 필요)
  • 굵기를 3개로 줄여야 용량이 감당된다
③ Pretendard 웹폰트교체
  • 100–900 전 굵기 · 라틴/한글 자폭 일관
  • 시스템 UI 폰트와 metric 유사해 이질감 적음
  • 한국 금융·업무 서비스에서 사실상 표준
  • 폰트 교체 — 확정된 시안 전체를 다시 봐야 한다
  • 현재 시안·감사 문서의 기준이 Noto Sans KR

3. 굵기 — 3단으로 축소

현재 스펙은 400·500·600·700 네 단계를 씁니다. 웹폰트로 가더라도 500과 600은 10~13px에서 육안 구분이 거의 안 되고, 굵기 하나당 한글 웹폰트 용량이 크게 늘어납니다. 결정적으로 Android가 실제로 갖고 있는 굵기가 정확히 400·500·700이라 — 600만 합성됩니다 — 이 세 단으로 맞추면 웹폰트 로딩에 실패해도 Android에서 위계가 유지됩니다. 400 · 500 · 700 세 단으로 줄이는 것을 권합니다.

4. 크기 — 12단 → 7단

감사 결과 코드에 12가지 크기가 흩어져 있습니다(7·9·10·11·12·13·14·16·18·20·24·48px). 확정 스펙이 쓰는 값만 남겨 7단으로 정리합니다.

5. 정리 — 이렇게 하면 동일해집니다

항목확정 필요 사항
폰트② Noto Sans KR 웹폰트 — 자체 호스팅 + font-display:swap. 한글 서브셋(unicode-range 분할)으로 초기 로딩 최소화
굵기400 · 500 · 700 3단만 로드. 600은 전부 500 또는 700으로 흡수
크기7단 스케일. 9px 이하 금지 · 임의 픽셀값 금지
숫자font-variant-numeric:tabular-nums — 웹폰트라 모든 플랫폼에서 동작 보장
폴백'Noto Sans KR', 'Apple SD Gothic Neo', 'Malgun Gothic', sans-serif — 로딩 실패 시에도 한글이 깨지지 않도록
렌더링-webkit-font-smoothing:antialiased는 macOS에서만 획을 가늘게 만든다. 플랫폼 간 동일하게 하려면 쓰지 않는 편이 낫다 — 확정 필요

결론 — 색·간격·라운딩·밀도는 확정 스펙 그대로 어디서나 동일합니다. 폰트만 웹폰트로 고정하면 요청하신 "맥·윈도우·모바일 동일"이 성립합니다. 웹폰트를 쓰지 않으면 Windows에서 위계와 금액 정렬이 무너지므로, 이건 선택이라기보다 D안이 성립하기 위한 전제에 가깝습니다.
