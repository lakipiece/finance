# 포트폴리오 수익 지표 체계 — 최종 정리

> 확정일: 2026-08-15 / 관련 커밋: `4ec92ca` → `79f6022`
> 이 문서가 **지표 정의의 단일 기준**이다. 화면·코드·문서가 어긋나면 이 문서를 기준으로 맞춘다.

---

## 1. 지표 정의 (용어 사전)

| 지표 | 정의 | 소스 |
|------|------|------|
| **투자원금** | 계좌 **누적입금** (원장 기록 계좌) | `account_cashflows` |
| **평균매수금액** | Σ(보유수량 × 평균매수단가), KRW 환산 | `holdings` |
| **평가금액** | Σ(보유수량 × 현재가), KRW 환산. 예수금은 현금 자산군 종목으로 포함 | `holdings` × `price_history` |
| **평가손익** | 평가금액 − 평균매수금액 (보유 종목의 가치 증감, 미실현) | 계산값 |
| **수익금액** | **평가금액 + 누적출금 − 누적입금** (실질 수익) | 계산값 |
| **수익률** | 수익금액 ÷ 투자원금 | 계산값 |
| **배당금액** | 누적 배당·분배금 (월별 집계는 배당 페이지, 당월 합계는 스냅샷 카드) | `dividends` |

핵심 구분: 기존의 "투자원금"은 사실 **평균매수금액**이었다. 이름을 분리하면서
투자원금은 "실제로 계좌에 넣은 돈"이라는 본래 의미를 갖게 됐다.

### 수익금액 공식이 이렇게 생긴 이유

```
계좌 항등식:  평가금액 = Σ입금 − Σ출금 + 총수익
∴ 총수익 = 평가금액 + Σ출금 − Σ입금
```

- 매매차익·배당 재투자·수수료·세금은 전부 평가금액에 이미 녹아 있어 **잔차로 자동 포착**된다.
- 출금에는 배당 인출뿐 아니라 **원금 회수도 포함**해야 어떤 경우에도 성립한다.
  (배당 출금만 더하면 원금 인출 시 수익이 과소계산됨)
- 배당을 공식에 또 더하면 이중계산 — `dividends`는 분석용 지표로만 쓴다.

## 2. 하이브리드 규칙 (가장 중요)

원장(입출금 기록)은 계좌별로 있거나 없다. **기준 결정은 반드시 계좌 단위**로 한다:

```
계좌마다:
  원장 있음(누적입금 > 0) → 기준 = 누적입금,     수익 = 평가액 + 출금 − 입금
  원장 없음               → 기준 = 평균매수금액,  수익 = 평가액 − 매수원가
그 다음에 합산한다.
```

**전체 합계끼리 비교하면 안 된다.** 원장이 1개 계좌(입금 2,500만)에만 있을 때
전체 평가액(2.6억)과 비교하면 수익률 +935% 같은 왜곡이 나온다 (2026-08-15 수정된 버그).

구현: [`lib/portfolio/metrics.ts`](../lib/portfolio/metrics.ts)
- `hybridTotals(perAccount, ledger)` — 계좌별 기준 적용 후 합산 (공통 코어)
- `snapshotMetrics(breakdown, events, date, totals)` — 스냅샷 1개용 래퍼.
  `account_breakdown`이 비어 있으면(값 갱신 전) 원장 적용 불가 → 매수원가 기준 폴백
- `cumulativeByAccount(events, date)` — 날짜 기준 계좌별 누적 입금/출금

`ledgerApplied`(원장 적용 여부)·`coversAll`(전 계좌 원장 보유)로 화면에서 기준을 표기한다.

## 3. 데이터 모델

### account_cashflows (입출금 원장)

| 컬럼 | 내용 |
|------|------|
| `account_id` | FK → accounts (CASCADE) |
| `flow_date` | 발생일 |
| `type` | `deposit` 입금 / `withdrawal` 출금 / `transfer_in` 이체입금 / `transfer_out` 이체출금 / `opening` 기초잔액 |
| `amount` | KRW, 항상 양수 (방향은 type이 결정) |

- **입금 계열** = deposit + transfer_in + opening / **출금 계열** = withdrawal + transfer_out
- **opening(기초잔액)**: 과거 입금을 소급하지 않고 기록 시작 시점의 계좌 평가액을 1건 넣는 앵커. 계좌당 1건.
- **계좌 간 이체**: 보내는 계좌 `transfer_out` + 받는 계좌 `transfer_in` 쌍으로 입력. 전체 합산에서 상쇄.
- 날짜별 이벤트로 쌓으므로 나중에 XIRR(금액가중 수익률)·연도별 투입금 분석 가능.

### snapshots.account_breakdown (jsonb)

```json
{ "<account_id>": { "value": 평가액, "cost": 평균매수금액 } }
```

- **값 갱신**(`POST /api/portfolio/snapshots/refresh-values`) 시 계좌별로 집계·저장.
- 스냅샷 목록·차트가 과거 시점의 하이브리드 지표를 계산하는 데 필요하다.
  (스냅샷 합계만으로는 계좌별 기준을 정할 수 없음)
- 비어 있는 스냅샷은 매수원가 기준으로만 표시 → "값 갱신" 1회로 해소.

### 역할 분리: valuation.ts vs metrics.ts

| 모듈 | 책임 |
|------|------|
| [`lib/portfolio/valuation.ts`](../lib/portfolio/valuation.ts) | **가격·환산**: 환율 fallback, KRW 판정, 가격 키 조회, KST 거래일 |
| [`lib/portfolio/metrics.ts`](../lib/portfolio/metrics.ts) | **수익 지표**: 하이브리드 기준 결정·합산, 누적 입출금 |

## 4. 화면별 적용 매트릭스

| 화면 | 투자원금/수익 계산 | 비고 |
|------|-------------------|------|
| 포트폴리오 대시보드 KPI | `hybridTotals` (포지션에서 계좌별 value/cost 집계) | 계좌 필터 반영. 섹터/태그 필터 중엔 원장 지표 비활성(계좌 단위 지표이므로) |
| 계좌 관리 → 계좌 모달 **입출금 탭** | 단일 계좌 직접 계산 | 입력 폼 인라인 (중첩 모달 없음). 요약: 투자원금·누적출금·평가금액·수익금액 |
| 스냅샷 목록 카드 | `snapshotMetrics` + `account_breakdown` | 수익·당월 배당 라인. 월별 그루핑(월별 최종/최초/전체 필터, `+N` 펼치기) |
| 자산 추이 차트 | `snapshotMetrics` (시점별) | 목록과 필터 연동(`?view=`). 평가액 바 + 평균매수금액 실선 + 투자원금 점선. 툴팁·KPI 동일 기준 |
| 스냅샷 편집 | 자체 계좌별 계산 (스냅샷 날짜 기준 누적) | 계좌 카드·모달 헤더에 투자원금/평가손익/수익금액. 과거 스냅샷은 그 시점까지의 입금만 반영 |
| 배당 페이지 | 해당 없음 (배당 분석 전용) | 월별/계좌별/종목별 집계 유지 |

KPI 카드 구성 (대시보드, 원장 있을 때):
`총 평가금액 / 투자원금 / 평가손익 / 수익금액(수익률) / 누적 분배금`
원장 없으면 기존 매수원가 기준 5장으로 폴백 ("입출금 미기록" 표기).

## 5. 운영 가이드

### 시작하기 (계좌별 1회)
1. 계좌 관리 → 계좌 카드 클릭 → **입출금 탭**
2. `기초잔액` 유형으로 현재(또는 기록 시작 시점) 평가액 1건 입력
3. 이후 실제 입금/출금/이체만 그때그때 기록

### 정확도를 위한 규칙
- **스냅샷에 예수금(현금)을 계속 입력**한다 — 평가금액이 정확해야 수익금액이 정확하다.
- 배당이 계좌에 들어와 재투자되면 아무것도 기록하지 않는다 (평가액에 이미 반영).
  은행으로 인출했을 때만 `출금`으로 기록.
- 스냅샷을 만들거나 입출금·보유내역을 크게 바꿨으면 **값 갱신**을 눌러
  `account_breakdown`을 최신화한다.

### 알려진 한계
- 종목 단위 실현손익 분해는 불가 (계좌 단위까지). 거래 원장이 없는 스냅샷 모델의 트레이드오프.
- 원장 미기록 계좌의 "수익"은 여전히 미실현 평가손익이다 (매매차익 미포착).
- USD 종목의 평균매수금액은 조회 시점 환율로 환산되므로 환율에 따라 변동한다.
  (수익금액은 원장 기준이라 이 문제가 없음 — 원장 기록을 넓힐수록 정확해진다)
